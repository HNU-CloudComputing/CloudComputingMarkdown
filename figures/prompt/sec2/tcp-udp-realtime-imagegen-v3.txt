FIGURE CONTRACT

Why this figure exists:
用同一次 A 丢失对比 TCP 和 UDP 对后续状态更新 B、C 的交付方式，由 TCP 队头阻塞自然推进到“应用层按消息语义取舍”。

One teaching question:
A 丢失后，B 和 C 为什么在 TCP 中等待，而在 UDP 中可以立即交付？

Beginner misconception to prevent:
- A、B、C 是应用层游戏状态更新，不是 TCP 包名。
- UDP 不会自动重传；覆盖或确认与重传是应用层的选择。
- 图中不得出现“ACK重传”。

Diagram role:
上下两条对齐的事件时间线对比图。

Required mechanism:
- 上方 TCP 时间线严格按四个时刻从左到右排列：t1 为 A 丢失，t2 为 B 到达接收缓冲区但不能交付，t3 为 C 到达接收缓冲区但不能交付，t4 为重传 A 到达后 A、B、C 按序交付。
- B 和 C 在 TCP 中只能先进入一个虚线的“接收缓冲区”，其右侧有一道橙色“队头阻塞”隔挡。重传 A 到达后，隔挡解除，三个更新作为一组按序交付。
- 下方 UDP 时间线使用完全相同的四个时刻：t1 为 A 丢失，t2 为 B 独立交付，t3 为 C 独立交付，t4 留空，明确表示不等待 A。
- 右侧只放一个紧凑的“应用层取舍”区域：高频状态 -> 新状态覆盖；关键事件 -> 确认与重传 + 请求编号。
- 底部只保留一句短结论“语义决定取舍”。

Details to leave in prose:
TCP 字节序号、RTO、拥塞控制、幂等处理、持久化。
